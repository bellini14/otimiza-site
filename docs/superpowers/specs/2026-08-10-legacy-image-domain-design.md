# Legacy image domain design

## Goal

Serve only images originating from the former WordPress site from `https://www.otm.com.br/wp-content/uploads/...`. Images added after the migration remain on the Sanity CDN.

## Context and scope

The Sanity production dataset has 535 image assets. The local legacy-media archive contains 1,309 files under `public/wp-content/uploads`. File-name matching identifies 242 unambiguous candidates, 19 candidates with duplicate names, and 274 Sanity assets with no legacy counterpart.

This change applies to image URLs rendered by posts (cover and inline images), case and client-logo content, and social/SEO image generation. It does not move or edit Sanity documents, upload new media, or change static images that already use local paths.

## Architecture

A checked-in manifest maps a Sanity image asset identifier to a legacy public path. A single resolver accepts a Sanity URL (including transformed URLs produced by `urlFor`) and:

1. extracts its immutable asset identifier;
2. returns the canonical `https://www.otm.com.br/wp-content/uploads/...` URL when the identifier is in the manifest;
3. otherwise returns the original URL unchanged.

The manifest is generated by a repository script rather than maintained by hand. The generator indexes the legacy archive and matches each Sanity asset using its identifier, original filename, and dimensions. It accepts only unambiguous matches. Duplicate or missing candidates are reported and omitted, which deliberately preserves the Sanity URL instead of risking the wrong image.

Only files referenced by the generated manifest are committed into `public/wp-content/uploads`. Vite copies this directory to the deployment output, so the files are served by the production domain without a new runtime service, proxy, or Sanity write.

## Components

- `scripts/generate-legacy-image-manifest.mjs` queries the public Sanity dataset, indexes local legacy media, validates candidates, and writes a deterministic manifest plus a report for unmatched assets.
- `src/lib/legacyImageUrl.js` owns URL resolution and has no React dependency.
- The render/query boundaries that currently consume `asset->url` or `urlFor(...).url()` call the resolver before passing an image URL to the UI or SEO layer.
- Static social-page generation uses the same resolver so generated HTML and browser-rendered pages agree.
- A media regression check verifies each manifest target exists under `public` and rejects manifest targets outside `wp-content/uploads`.

## Safety and fallback behavior

- A non-Sanity URL is returned unchanged.
- A Sanity URL that has no manifest entry is returned unchanged; this is the expected path for new images.
- The resolver never guesses from a filename at runtime.
- The generator refuses duplicate, missing, or unsafe paths and reports them for explicit review.
- Builds and tests do not need a live Sanity request: the generated manifest is committed. Live access is used only when intentionally regenerating it.

## Verification

Tests first cover three contracts: a mapped legacy asset resolves to the OTM URL, an unmapped/new Sanity asset remains on the Sanity URL, and an unrelated URL is unchanged. The regression test verifies manifest files are deployable. Focused page and social-generator tests assert that their output uses the shared resolver.

Before publishing, run the focused tests and a production build with `VITE_SITE_URL=https://www.otm.com.br`. The full suite currently has 14 known baseline failures unrelated to this work; those failures are recorded separately and are not changed by this scope.
